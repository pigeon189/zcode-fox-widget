## 1) 总体印象

这套 UI 的底子明显高于一般「个人小挂件」：语义色、对比度、禁用态、焦点环、`prefers-reduced-motion`、角色配色派生、遮挡叠层都做过一轮系统清理（代码里的 U2/U8/U10/U12/U26/U31 等注释能对上），气泡几何与 1026×700 设计稿严格同构，浅色档「整套 chrome 跟随角色色」也是一致性上的加分项。**问题不在审美，而在两处「说好了却没落地」**：一是主题「跟随 WorkBuddy」这条最显眼的承诺其实整条失效（P0-1），二是深色档被当成「原生就够用」放过的复选框，在暗色面板上彻底看不见（P0-2）——两者都在用户每天会看到的路径上。

最值得改的三件事：

1. **修 `themeIsDark()` 的变量名**（P0-1，3 行）：现在「跟随 WorkBuddy」恒等于「跟随操作系统」，README 承诺的「WorkBuddy 里换主题 10 秒内跟变」完全没生效，而且菜单/面板/气泡整体会停在错误主题上；
2. **深色档补自绘复选框**（P0-2）：`避让滚动条 / 隐藏菜单按钮 / 等确认提醒` 三个开关在深色下是 16×16 的「隐形方块」，用户根本看不到这三个开关存在；
3. **把「原生 vs 自绘」的两套控件合并成一套**（P1-1）：浅色自绘滑块/复选框、深色用原生，导致同一控件在换主题时轨道粗细、圆点大小、描边、选中色全变，这是目前一致性上最刺眼的一处。

其余问题集中在「配置面板的信息密度与对齐」（行高 18/22/28 三档、单按钮行错位）、「数值格式口径」（`¥ 1.22` vs `¥1.22`、积分无千分位、tokens 同列混用「万」和「2,000」）、以及「超长数据的兜底」（10 位积分撑出气泡安全区、长模型名把用量记录面板撑到 628px）。CSS 侧没有设计 token，336 行 CSS 里 13 种字号、15 种圆角、10 种过渡时长、4 份逐字重复的阴影——这是后续迭代真正的成本所在。

## 3) 详细发现

### P0-1 「跟随 WorkBuddy」主题完全失效

**现状**

```js
// lib/widget.js:856   —— 端口化时把 zcodeTheme 改名成了 hostTheme（声明与轮询都改了）
var hostTheme = 'system' // 'light' | 'dark' | 'system'：WorkBuddy 当前主题
// lib/widget.js:864-870  —— 但判定函数漏改，读的是从未声明的 zcodeTheme
function themeIsDark() {
  if (themeMode === 'dark') return true
  if (themeMode === 'light') return false
  if (zcodeTheme === 'dark') return true     // ← zcodeTheme 未声明，恒为 undefined
  if (zcodeTheme === 'light') return false
  return systemPrefersDark()                 // ← 于是「跟随 WorkBuddy」永远等于「跟随系统」
}
```

实测（headless Edge，OS 为浅色，服务端已把宿主观测写成 dark）：

```json
// /whale/host-theme.json
{"ok":true,"theme":"dark","raw":"dark","source":"host-window",
 "file":".../plugin-data/host-theme-observed.json","observed":{"dark":1,"at":1792245099793}}
// 页面侧
{"htmlDark":false,"osDark":false,"themeMode":"system","zcodeThemeType":"undefined"}
```

**问题**
README 明确承诺「『跟随 WorkBuddy』三层判定（DWM 暗色标志观测 > 配置 > 系统），WorkBuddy 里换主题 10 秒内跟变」（`README.md:92`、`README.md:364`），`lib/host-theme.mjs` 也确实把三层判定都实现了、`pollHostTheme()` 也每 10 秒在拉——但最后一跳断了：判定函数读的是另一个名字，所以只要用户把主题选成「跟随 WorkBuddy」，挂件就只跟操作系统。WorkBuddy 用深色 + 系统浅色（或反之）时，菜单、二级面板、气泡全部是错的主题，而且**任何后续修复都建立在「主题能跟随」这个前提上**，所以它排第一。
注：这不是笔误级的小 bug——`main` 分支（ZCode 版）里对应位置是 `var zcodeTheme`（`git show main:lib/widget.js:849`），说明是移植时改漏，非设计如此。

**建议**
把判定函数改成读 `hostTheme`，并顺手把注释里的旧名词换掉：

```js
  function themeIsDark() {
    if (themeMode === 'dark') return true
    if (themeMode === 'light') return false
    // 跟随 WorkBuddy：hostTheme 由 pollHostTheme() 每 10s 刷新（三层判定见 lib/host-theme.mjs）
    if (hostTheme === 'dark') return true
    if (hostTheme === 'light') return false
    return systemPrefersDark() // hostTheme === 'system'：宿主也是跟随系统
  }
```

可选的加固（防回归）：在 `tools/selftest.mjs` 里断言 `lib/widget.js` 不再出现 `zcodeTheme` 字样，或在 `applyTheme()` 里 `diag('theme ' + themeMode + '/' + hostTheme)`。

**实现方式**
只改 `lib/widget.js` 的 `themeIsDark()`（864-870 行），共 2 个标识符。`applyConfig()`（5392 行附近）已经通过 `setTheme(d.theme)` 调用 `applyTheme()`，`pollHostTheme()` 在 `next !== hostTheme` 时也会重新 `applyTheme()`，所以改完即生效，无需动初始化顺序、无需动 `desktop/*`。**与 v2 气泡格式无关**（不涉及 `bubbleContent.v2`/`steps`）。浮层端不需要单独改：浮层与浏览器加载同一份 `widget.js`、同一份 `/whale/host-theme.json`。改完要重启挂件服务（前端 `Cache-Control: no-store`，刷新即可）。

**验收标准**
1. 系统浅色、`plugin-data/host-theme-observed.json` 写 `{"dark":1}`、主题选「跟随 WorkBuddy」→ 刷新页面后 `<html>` 带 `zcwv-theme-dark`，菜单底 `rgba(43,43,43,.96)`；
2. 把该文件改成 `{"dark":0}`，10 秒内（两次轮询）菜单自动回到浅色；
3. 主题手动选「浅色模式」时，即使观测为 dark 也保持浅色（`themeMode` 优先）；
4. 删掉观测文件、`preferences.json` 写 `{"theme":"dark"}` → 仍为深色（第二层生效）。

### P0-2 深色档未勾选的复选框不可见

**现状**

```js
// lib/widget.js:359-369  —— 自绘复选框，但整条规则被 :root:not(.zcwv-theme-dark) 排除
'.zcwv-check{width:16px;height:16px;accent-color:var(--zcw-accent);cursor:pointer;flex:0 0 auto}',
':root:not(.zcwv-theme-dark) .zcwv-check{appearance:none;-webkit-appearance:none;position:relative;' +
  'box-sizing:border-box;border:1px solid var(--zcw-ink-input);border-radius:4px;background:var(--zcw-card)}',
// lib/widget.js:385  —— 深色档只有 token，没有控件规则
':root.zcwv-theme-dark{--zcw-cs:dark;...;--zcw-ink-input:rgba(255,255,255,.2);...}',
```

放大 10× 的实测截图（同一颗「避让滚动条」复选框，左浅色 / 右深色）：

- 浅色：白底 + 1px 圆角描边，清晰可见；
- 深色：整块空白。像素采样：复选框区域 `#3b3b3b`，面板底 `#333333`（对比 ≈1.09:1）。

`getComputedStyle` 也印证：深色档 `appearance:auto`、`border-radius:0px`、`background:rgba(0,0,0,0)`——即完全交回 UA 绘制，而 Chromium 在 `color-scheme:dark` 下给未勾选复选框的填充色就是 `#3b3b3b`、无可见描边，正好压在 `rgba(43,43,43,.96)` 的面板底上。

**问题**
深色档里 `避让滚动条`（菜单第 12 行）、`隐藏菜单按钮`（第 13 行）、`等确认提醒`（第 10 行）这三个开关的**未勾选态完全看不见**——用户看不到「这里有个开关」，只能靠已勾选的 `气泡`/`每轮消耗提示` 反推行尾那一小团深灰是什么。这属于「控件消失」级别的可用性缺陷，不是配色偏好。

**建议**
把自绘复选框推广到两套主题（浅色档的观感不变），深色只换 token，并在深色 token 里补 `--zcw-check-mark`：

```js
// 1) 去掉两处 :root:not(.zcwv-theme-dark) 前缀（363 / 365 / 368 行），改为全局：
'.zcwv-check{appearance:none;-webkit-appearance:none;position:relative;box-sizing:border-box;' +
  'width:16px;height:16px;border:1px solid var(--zcw-ink-input);border-radius:4px;' +
  'background:var(--zcw-card);cursor:pointer;flex:0 0 auto}',
'.zcwv-check:checked{background:var(--zcw-accent);background-image:var(--zcw-role-ink-grad,none);border-color:var(--zcw-accent)}',
'.zcwv-check:checked::after{content:"";position:absolute;left:4px;top:1px;width:5px;height:9px;' +
  'border:solid var(--zcw-check-mark,#fff);border-width:0 2px 2px 0;transform:rotate(45deg)}',

// 2) 深色 token 里补对勾颜色（applyBubbleInk 在深色档会 removeProperty，所以必须由 token 兜底）
':root.zcwv-theme-dark{...;--zcw-check-mark:#fff}',
```

深色档的实际观感：未勾选 = `#2b2b2b` 底 + `rgba(255,255,255,.2)` 描边（对面板底 ≈2.6:1，图形元素达 3:1 档偏下限，可再提到 `.28`）；勾选 = `#4099ff` 填充 + 白勾。

**实现方式**
改 `lib/widget.js` 的 `css` 数组：363-369 行去前缀、385 行加 `--zcw-check-mark:#fff`。**不动** `applyBubbleInk()` 的深色分支（它继续 `removeProperty('--zcw-check-mark')`，token 兜底即可）。不需要改 `desktop/*`；纯 CSS，不影响任何持久化格式或 v2 气泡结构。

**验收标准**
1. 深色档菜单里三个未勾选开关肉眼可见（10× 放大后能看清 1px 圆角描边）；
2. 勾选后是纯色填充 + 白勾，与浅色档形态一致（同尺寸、同圆角、同描边宽度）；
3. 用户手选接近白色的角色墨色（浅色档）时对勾仍可见（`readableOn` 逻辑保留）。

### P1-1 同一控件两套实现：滑块与复选框随主题变形态

**现状**

```js
// lib/widget.js:194-199  浅色档：自绘轨道 4px、圆点 13px、容器高 14px
':root:not(.zcwv-theme-dark) .zcwv-range{appearance:none;-webkit-appearance:none;height:14px;background:transparent}',
':root:not(.zcwv-theme-dark) .zcwv-range::-webkit-slider-runnable-track{height:4px;border-radius:2px;' +
  'background:linear-gradient(to right,var(--zcw-accent) 0 var(--zcw-range-pct,50%),rgba(0,0,0,.14) ...',
':root:not(.zcwv-theme-dark) .zcwv-range::-webkit-slider-thumb{...;width:13px;height:13px;border-radius:50%;...;margin-top:-4.5px}',
```

实测同一颗「大小」滑块：

| | 轨道 | 圆点 | 容器高 | `appearance` |
| --- | --- | --- | --- | --- |
| 浅色 | 自绘 4px，未到达段带 `inset` 发丝描边 | 13px，角色色 | 14px | `none` |
| 深色 | 原生，细白底线 + 蓝色填充 | 系统圆点 | 16px | `auto` |

**问题**
换一次主题，滑块就从「细轨 + 角色色圆点」变成「系统蓝 + 白轨」，高度也差 2px（同一行的行高会跟着变，见 P1-2）。复选框同理（`border-radius` 4px vs 0px）。浅色档那条自绘规则当初是因为「原生空槽颜色跟着 accent 明度翻」才写的（代码注释 185-193 行讲得很清楚），但深色档的原生表现并没有被验证过——实际是「亮蓝 accent + 浅色轨道」，与深色档中性 chrome（`#2b2b2b` / `#d4d4d4`）不是一套语言。

**建议**
让自绘规则两套主题共用，只把「不适合深色」的两个常量提成 token：

```js
// token（浅色/深色各给一份）
':root{...;--zcw-range-track:#00000024;--zcw-range-h:14px;--zcw-range-thumb:13px}',
':root.zcwv-theme-dark{...;--zcw-range-track:#ffffff24}',

// 规则去前缀，轨道底色换成 token
'.zcwv-range{appearance:none;-webkit-appearance:none;height:var(--zcw-range-h);background:transparent;flex:1;min-width:0}',
'.zcwv-range::-webkit-slider-runnable-track{height:4px;border-radius:2px;' +
  'background:linear-gradient(to right,var(--zcw-accent) 0 var(--zcw-range-pct,50%),var(--zcw-range-track) var(--zcw-range-pct,50%) 100%);' +
  'box-shadow:inset 0 0 0 1px var(--zcw-range-track)}',
'.zcwv-range::-webkit-slider-thumb{appearance:none;-webkit-appearance:none;background:var(--zcw-accent);' +
  'background-image:var(--zcw-role-ink-grad,none);width:var(--zcw-range-thumb);height:var(--zcw-range-thumb);' +
  'border-radius:50%;border:none;margin-top:calc((4px - var(--zcw-range-thumb)) / 2)}',
```

（深色档想保留一点系统感也没问题，但**两套主题必须同尺寸同结构**，否则行高会跳。）

**实现方式**

### P1-4 数值与货币格式三套口径

**现状**

```js
// lib/widget.js:3498-3503  积分：不分组、不带单位
function formatCredit(n) { ... return (Math.round(v * 100) / 100).toFixed(2) }
// lib/widget.js:3674-3679  余额：¥ 与数字之间**有**空格
function fmt(balance, currency) { ... return currency === 'CNY' ? '¥ ' + fixed : fixed + ' ' + currency }
// lib/widget.js:3885-3890  紧凑额：¥ 与数字之间**没有**空格
function fmtCompact(n, currency) { ... return c === 'CNY' ? '¥' + fixed : c === 'USD' ? '$' + fixed : fixed + ' ' + c }
// lib/widget.js:3489-3495  tokens：≥1e8 用「亿」、≥1e4 用「万」、否则 en-US 千分位
function formatTokens(n) { if (v >= 1e8) return (v / 1e8).toFixed(2) + ' 亿'; if (v >= 1e4) return (v / 1e4).toFixed(1) + ' 万'; return v.toLocaleString('en-US') }
```

同屏可见的三处不一致（截图 03 与 05、71）：

- 用量记录：`63.00 积分（≈¥1.22）· 86.1 万` 与下一行 `0.00 积分（≈¥0.04）· 2,000` —— 同一列上「万」与「2,000」并存；
- 按压泡泡编辑器预览：`¥ 0.00`（有空格），与上一行同源的用量记录 `¥1.22`（无空格）；
- 气泡超长积分实测：`2962962965.97`（10 位无千分位），旁边的 tokens 却是 `86.1 万`。

**问题**
这是「同一种量在三处写法不同」的典型：货币符号空格 2 种、token 量纲 2 种、积分完全没有量纲处理。用户在「用量记录」里对账时，同一列数字宽度不一、量纲不一，扫读成本明显上升；`¥ 1.22` / `¥1.22` 更是同一屏内就能看到的破绽。

**建议**
收敛成两个纯函数，全仓只走它们：

```js
// 1) 统一「符号 + 数字」的拼接（CM 里不空格，其它币种空格）
function fmtMoney(n, currency) {
  var v = Number(n)
  if (!isFinite(v)) return '--'
  var fixed = v.toFixed(2)
  var c = currency || 'CNY'
  return c === 'CNY' ? '¥' + fixed : c === 'USD' ? '$' + fixed : fixed + ' ' + c
}
// 2) 积分与 tokens 共用一套量纲：≥1e8 → 亿，≥1e4 → 万，其余千分位
function fmtMagnitude(n, unit) {
  var v = Number(n) || 0
  if (v >= 1e8) return (v / 1e8).toFixed(2) + ' 亿' + (unit || '')
  if (v >= 1e4) return (v / 1e4).toFixed(1) + ' 万' + (unit || '')
  return v.toLocaleString('en-US') + (unit || '')
}
// formatCredit → fmtMagnitude(v, '') 的两位小数版本；formatTokens → fmtMagnitude(v,'')
```

若不愿改气泡主数字的量纲（`2962962965.97` 在 1e8 以下仍是完整数字，可读性更好），至少让 `formatCredit` 走千分位：`v.toLocaleString('en-US',{minimumFractionDigits:2,maximumFractionDigits:2})`。

**实现方式**
`lib/widget.js`：`fmt`(3674)、`fmtCompact`(3885)、`formatCredit`(3498)、`formatTokens`(3489) 四个函数 + 各自调用点（`render()` 4 处、`builtinTurnCostParts()` 3 处、`renderQuotaRows`/`quotaBalanceSub`、用量记录面板 5430+ 行）。**注意 v2 气泡**：`{cost}` / `{tokens}` / `{credit}` 占位符的展开值（`templatePreviewCtx` 6665-6668、`stepToLines`）会一起变——这是期望行为（预览与真泡同源），但要在 CHANGELOG 里写一句「占位符数值格式变更」，避免用户误以为自定义模板失效。浮层端不需要改。

**验收标准**
1. 全仓搜 `'¥ '` 只剩一处（或零处），同屏不再出现 `¥ 1.22` 与 `¥1.22` 并存；
2. 用量记录「模型排名」列的 tokens 全列同量纲（要么全「万/亿」，要么全千分位）；
3. 气泡主数字 ≥1 万时带千分位或「万」；
4. `tools/selftest.mjs` 里钉死格式的断言同步更新（若有）。

### P2-6 全局没有字体栈

**现状**

```js
// lib/widget.js:81   —— 唯一的字体声明是"继承"
'.zcwv-root{...;font-family:inherit;...}',
// lib/server.mjs:1121-1123  —— 页面里没有任何 font-family
<style>
  html,body{margin:0;padding:0;width:100%;height:100%;overflow:hidden;background:${bg}}
</style>
```

实测实际渲染字体（`CSS.getPlatformFontsForNode`）：`menuRow / amount / hint / rolePick` 全部是 **Noto Sans SC**，来源是"本机恰好装了它 + 浏览器默认 CJK 字体"，不是我们指定的。

**问题**
字体完全交给系统默认：装了 Noto Sans SC 的机器是黑体观感，没装的中文 Windows 通常会落到宋体/微软雅黑（不同 Chromium 版本默认不同），同一份挂件在不同机器上字形、字重观感会明显不同；而气泡里 `font-weight:800` 的大数字在宋体回退下会显得非常突兀。这是"一致性"里唯一无法用 CSS 变量兜住的一项。

**建议**

```js
// 放到 :root 上（气泡与面板共用）
':root{...;--zcw-font: "Noto Sans SC", "Microsoft YaHei UI", "Microsoft YaHei", "PingFang SC", "Hiragino Sans GB", system-ui, sans-serif}',
'.zcwv-root{...;font-family:var(--zcw-font);...}',
// server.mjs 的 body 也同步（避免面板里任何继承点落回默认）
```

只声明不打包字体（不引入体积、不联网），靠系统字体族顺序收敛观感。

**实现方式**
`lib/widget.js:81` + `lib/server.mjs:1122`。**不影响 v2 气泡**（字号是相对的 `calc(u*n)`，换字体只会改变字宽，`fitBubbleLines` 会自动重排）。浮层端共用同一页面，无需单独改。

**验收标准**
1. `getComputedStyle(document.querySelector('.zcwv-menu-row')).fontFamily` 返回上面的栈（而不是单一系统字体）；
2. 在无 Noto Sans SC 的机器上仍落到微软雅黑（不是宋体）；
3. 气泡三行文字宽度变化后仍不越界（`fitBubbleLines` 正常介入）。

## 4) 明确不建议改的部分及原因

1. **气泡几何（1026×700 设计稿 / SVG 路径 / 尾巴与两枚小气泡）**：`viewBox`、`.zcwv-img` 的 `59.45%` 与 `top:40.55%` 锚点、`.zcwv-gif` 的 `left:44.25% top:38%` 全是按同一张设计稿算出来的；动一处要连带 `fitBubbleLines` 的 560u 安全宽度、编辑器迷你预览（1026 比例）、角色 PNG 的透明边钳制（`topPadFor`/`bottomPadFor`）。收益低、回归面极大。
2. **浅色档「整套界面跟随角色色」**：这是 2026-10-06/07 定稿的设计决策（`--zcw-role-ink` 只在浅色写入，深色保持中性）。P1-1 只统一控件**形态**，不要顺手把深色也染上角色色——那会把"深色 = 中性、浅色 = 角色主题"的既有语义打乱。
3. **`.zcwv-overlay{transition:none}`（86 行）与浮层定位策略**：注释写明"透明窗口对 left/top 做过渡，Chromium 会把内容画到偏离窗口的位置"。吸附少一段滑动动画是**已知代价**，不是缺陷；别为了动画把它改回去。
4. **`prefers-reduced-motion` 的 `.01ms` 兜底 + `.zcwv-flow` 单点停用（409-414）**：实测媒体查询生效（菜单/本体 `transition-duration:1e-05s`）。这套写法比"全局 `animation:none !important`"精确（保留了功能性状态变化），是正确做法。
5. **浮层窗口形态（`type:'toolbar'`、`focusable:false`、`setOpacity` 隐身、不 `setBounds`）**：这是 issue #2「宿主冻结」的修复结论，属于窗口层硬约束；任何 UI 改动都不应触碰。
6. **菜单按钮"悬停才出现"**：`trackPointerAt` 用「角色命中 ∪ 按钮矩形 ∪ chrome」三类命中控制可见性（5100-5117），已经解决了"按钮在角色身上点不到"的问题；改成常显会破坏"桌面浮层不打扰"的初衷。
7. **`--zcw-u` 相对字号体系（`calc(var(--zcw-u) * N)`）**：气泡内所有字号都是相对设计稿宽度算的，缩放时整体等比，这是对的；不要换成固定 px（会破坏 0.6–2.5 缩放的一致性）。
8. **`type:'toolbar'` 之外不要动 `desktop/main.cjs` 的窗口创建**；本次报告里没有任何一条要求改窗口层（浮层与浏览器共用同一份 `widget.js`，样式修复天然双端一致）。

## 5) 实施顺序

每条尽量对应一个独立提交（`fix(ui): …` / `style(ui): …`），P0/P1 提交后各跑一次 `node tools/smoke-ui.mjs` + `node tools/selftest.mjs`。

**P0（先修，两个都是"用户每天看到"的）**

1. **P0-1** 主题跟随（`themeIsDark()`：2 个标识符）—— 最小改动、最大收益，先落地以便后续所有主题相关验收都在"跟随"正确的前提下做。
2. **P0-2** 深色复选框可见（去 `:root:not(.zcwv-theme-dark)` 前缀 + `--zcw-check-mark`）。

**P1（一致性与体验缺陷，按依赖关系排）**

3. **P1-1** 控件两套实现合一（滑块 + 复选框）—— 与 P0-2 同一批 CSS，建议紧接其后，一次把"控件层"收敛干净。
4. **P1-2** 菜单行高/间距（`min-height:28px`、`margin:4px 0`）—— 会被 P1-1 的滑块高度变化影响，必须在它之后做。
5. **P1-3** 记账页单按钮行对齐（纯结构，独立）。
6. **P1-4** 数值/货币格式收敛（`fmt`/`fmtCompact`/`formatCredit`/`formatTokens`）—— 与 P1-6 相关（量纲决定会不会溢出），先做格式再做兜底。
7. **P1-6** 超长积分兜底（`overflow-wrap` + 预览同步）—— 依赖 6 的结论。
8. **P1-7** 用量记录长模型名（`min-width:0` + 省略 + `title`）。
9. **P1-5** 气泡标题统一（4 处字符串 + 全角冒号）—— 文案改动，独立可回滚。
10. **P1-8** 「再点角色」文案/反馈（README + 3 行动画），最后做，因为它要等标题/文案都定稿后再统一改文档。

**P2（打磨，可批量或按需）**

11. **P2-4** 菜单补 `color`（1 行，顺手做）。
12. **P2-2** 点击目标 ≥24px。
13. **P2-3** 气泡小字对比度（复用 `ensureContrast`）。
14. **P2-7** 面板 `box-sizing`。
