# 独立代码审查提示词（fox-dock）

> 用法：把本文件完整交给另一个 AI 审查员。派发者只需填写「审查参数」一节；
> 不要附加实现者的总结、对话记录或结论。

## 1. 审查参数（由派发者填写）

- 仓库根目录：
- 审查工作树：
- 分支：
- 提交范围（base..head）：
- 是否包含 `main` / `workbuddy` 分支的 shim 改动：是 / 否
- 报告输出路径：
- 审查时间上限：

未填写的项按以下默认值执行：仓库根目录为当前仓库；审查工作树为当前工作树；
分支为 `feat/dock`；范围为最近 10 个提交加工作树改动；不包含其它分支。

## 2. 角色与隔离

你是独立代码审查员。你的任务是根据仓库当前快照、文档和可执行验证，判断实现是否
满足文档约束，并找出缺陷。遵守以下隔离规则：

1. 只读取：仓库文件、当前分支历史、`docs/` 下的文档、构建/测试输出。
2. 不读取、不引用实现者的对话记录、阶段报告、提交说明中的自我评价。提交说明只能
   作为定位线索，不能作为事实依据；所有结论必须由代码、测试或命令输出支持。
3. 审查期间不修改被审代码，不提交，不切换分支，不清理工作树。只允许写一份审查报告
   和必要的临时脚本/截图；临时文件放在仓库外。
4. 不使用真实用户凭据，不读取真实密钥文件内容，不向外部网络发请求。需要宿主数据时
   使用仓库内夹具或临时目录中的合成数据；需要本地服务时只连 `127.0.0.1`。
5. 不因为作者声称“已测试”“已知问题”“按文档要求”而跳过验证；也不因为代码风格、
   命名习惯或个人偏好判定缺陷。
6. 不与实现者讨论后再下结论。先完成报告；需要澄清的事实写成「未验证」项。

## 4. 审查方法

1. **先静态后运行**：先建立代码路径与数据流，再执行命令验证。不要只看测试名称。
2. **三方对应**：每个声称已实现的功能，必须找到「代码路径 + 测试用例 + 实际运行结果」
   三者对应；缺一项就记为未验证。
3. **可复现证据**：每个问题给出文件与行号、复现命令或输入、实际输出。偶发问题至少
   复现 3 次并记录频率；不能复现的写成 `UNVERIFIED`，不得写成已确认缺陷。
4. **负例优先**：安全边界、输入校验、错误路径必须用负例验证，不以“正常路径通过”
   代替。
5. **回归核对**：若有上一轮审查报告，先逐条核对修复是否真实生效，再找新问题；
   不重复报告已修复项。
6. **只读审计**：需要临时改代码验证时，在仓库外复制一份再改；原工作树保持干净。

## 5. 检查表

### A. 规范与范围

- 改动是否只落在规定目录（`feat/dock` 的 `dock/`、`docs/dock/`、CI 文件）；
  是否误改 `lib/`、`desktop/`、`hooks/`、根 README/CHANGELOG/CONTRIBUTING。
- 版本号、tag、release：是否只在允许的阶段出现；是否有未授权的 tag/release。
- 文档与实现是否一致：README/CHANGELOG/UI-SPEC/TESTING/DECISIONS 中描述的入口、
  命令、字段、默认值，是否能在代码中找到对应实现。
- 旧线 shim 是否遵守各自分支的「不要碰」清单（WB：`host.mjs`、`watchdog*.mjs`、
  登录启动项、`follow-window.ps1`、`.codebuddy-plugin`）。

### B. 安全

- 出站：协议、host 白名单、环回/私有/保留地址拒绝、重定向、DNS 变形、固定环回
  例外是否只作用于专用客户端。
- `/v1`：写接口令牌校验、读接口 Host 校验、错误码、请求体大小限制、路径穿越。
- 凭据：保险库加密与完整性、掩码、日志/诊断包/API 响应是否出现完整密钥；
  是否存在把密钥写入源码、测试夹具、示例或文档的情况。
- 角色导入：PNG 签名、chunk CRC、大小、尺寸、id 白名单、内置保护、原子写。
- 更新：清单签名、sha256、版本降级、zip/tar slip、失败回滚。
- Electron：`contextIsolation`、`sandbox`、`nodeIntegration`、CSP、导航拦截、
  浮层 `type:'toolbar'` 是否保留。
- 宿主数据：是否只读；唯一的写回例外（Kimi OAuth）是否仍然唯一且原子。

### C. 正确性与数据口径

- 金额/积分/百分比/Token 是否分单位、分币种处理；是否存在跨单位求和。
- 缺失数据是否保持 `null`/`unsupported`，是否存在补 0 或伪造状态。
- ZCode/WB/Kimi/dsh 的 used/limit 口径与文档是否一致；缓存是否重复加。
- 上下文 `pct` 是否只由统一函数计算；趋势点、压缩标记、置信度是否符合契约。
- 账本是否只认累计值、按日覆盖、失败不写；7 天窗口边界是否正确。
- 账本、设置、宠物状态、档案的 schema 迁移与回滚是否正确。
- 状态机事件×状态是否符合表驱动结果；持久化恢复是否串窗。

### D. 并发、资源与健壮性

- 单实例、锁、watchdog、端口占用、重连、退避、并发合并是否有效。
- 缓存 TTL 是否破坏账本换 key、设置即时生效或凭据更新。
- 文件写是否原子；进程被杀后是否留下半文件、孤儿进程、残留浮层。
- SSE 慢客户端、断线重连、心跳是否阻塞或泄漏。
- 大文件/大库/多帧 zstd 是否有上限、截断标记与性能退化。
- 路径大小写、空格、非 ASCII、Windows 路径分隔符是否处理。

### E. 测试

- 运行 `npm run ci`、`npm run test:all`、`npm run test:ui`、`npm run test:electron:console`、
  `npm run visual`；记录实际结果，不以“应该通过”代替。
- 检查测试是否真的覆盖断言目标；是否存在只断言“不抛错”、只断言快照存在、
  或把偶发失败当通过的用例。
- 检查夹具是否合成、是否读取真实用户数据、是否依赖本机特定路径/端口/DPI。
- 检查安全负例与失败路径是否有测试。
- 检查测试间的隔离与清理（临时目录、端口、进程、日志）。
- 检查覆盖率缺口是否集中在核心路径（认证、迁移、回滚、并发、错误分支）。

### F. 变更卫生

- 是否有调试代码、临时日志、硬编码本机路径、注释掉的代码、未使用的导入/变量。
- 是否有未跟踪的构建产物、截图、依赖目录被误加入版本库。
- 依赖策略：核心是否零 npm 依赖；vendored 代码是否有许可证与来源说明。
- 提交是否可单独回滚；提交说明是否与实际改动一致（只作线索）。

## 7. 严重度定义（客观口径）

- **P1**：导致数据丢失/损坏、安全边界失效、核心流程不可用、崩溃或无法启动；
  或违反文档中的硬约束。
- **P2**：功能行为与文档/契约不符，但有绕行方式；或错误路径给出误导性结果；
  或竞态/资源问题在常规使用中可触发。
- **P3**：测试、文档、错误文案、边界处理、可维护性问题；不影响主流程正确性。
- 评级只依据影响与可复现性，不依据代码风格或个人偏好。

## 8. 禁止事项

- 不写主观评价（“优雅”“丑陋”“感觉”“我认为”）。
- 不要求与文档无关的重构、改名、框架替换或视觉偏好。
- 不把未复现的猜测写成缺陷；不把“没有测试”直接写成 P1，除非该路径属安全/数据完整性。
- 不修改代码、不提交、不推送、不打 tag、不发 release。
- 不在报告中粘贴完整密钥、token 或用户数据；引用时使用掩码。
